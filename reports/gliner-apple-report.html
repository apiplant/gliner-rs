Absolute times must not be compared across these two harnesses. Mac MLX uses automatic cache retention; iPhone MLX uses the platform policy of 20 MiB with clearing after each request. Candle has lower model-load times in these warmed-cache trials. The first recorded iPhone Small Candle smoke run took 7.656 s to load; subsequent formal trials took approximately 0.14 s. Load-inclusive peak RSS can include mapped file pages, copies and temporary buffers, and does not establish a permanent twofold resident-memory difference. Implementation cost and remaining limits

The Rust model is reused. The required DeBERTa change avoids allocating an unsupported F64 mask-floor temporary before converting it to F32; the final masking value is preserved. Metal is opt-in and initialization failure is an error, with no CPU fallback. The iPhone integration uses a Rust static library and a small C boundary called from SwiftUI. A Swift rewrite is not required to use Metal or build an iPhone app.

These workloads establish numerical agreement and local performance for the tested checkpoints. They do not measure dataset-level extraction quality, energy, sustained thermal behavior, every Apple device, or minimum supported OS versions. Similar output does not by itself establish similar performance or memory use.

01Scope and repository structure

Both backends live in the existing repository. Rust/Candle now supports opt-in Metal in addition to its existing CPU/CUDA paths. The Swift implementation uses MLX tensor operations. Both runtimes supply their own Metal kernels; no custom Metal Shading Language kernels were added for this project. The following implementation and runtime sections primarily document the Swift/MLX path.

Supported tasks: entity extraction, single/multi-label classification, relations, structured records in natural/latent/anchorless modes, choice fields, entity attributes, regex validators, overlap policies, padded batches, and long-document chunking. Legacy Span checkpoints, ModernBERT encoders and quantized weights are outside the implemented scope.

Declared deployment targets: macOS 14 and iOS 17. Actual execution was verified on macOS 27.2 and a physical iPhone 17 Pro; minimum OS versions were not tested on devices running those versions.

DeBERTa attention

For input IDs and mask shaped [B,T], hidden states have shape [B,T,H]. Attention projections are reshaped to [B,A,T,H/A]. The implementation combines content-to-content, content-to-position and position-to-content scores, using the same relative-position bucketing and masking semantics as the reference.

S = (Q Kᵀ + gather(Q Rkᵀ, c2p) + transpose(gather(K Rqᵀ, p2c))) / √(3 · head_dim)
context = softmax(mask(S)) V
attended = LayerNorm(Wo(context) + hidden)
next_hidden = LayerNorm(W2(GELU_erf(W1(attended))) + attended)

Relative embeddings are normalized and their layer-specific projected keys/queries are computed once during model initialization. The pinned checkpoints use shared attention keys, 256 position buckets and LayerNorm ε = 1e-7. Dropout is omitted in inference.

Memory complexity: this encoder explicitly constructs dense attention scores and relative-position index matrices. Attention storage scales as O(B · A · T²). A local mask in the Boundary head does not make the DeBERTa encoder sparse. The current implementation does not use a custom fused disentangled-attention kernel.

Boundary and record configuration

The tested checkpoints use boundary dimension 128, two boundary attention layers with four heads and window 128, one refinement layer, shared pool size 192 and boundary top-k 32. Relation pairs are capped at 64; the record head has 32 learned instance queries. Candidate selection and exclusivity constraints preserve reference tie-breaking. Scalar exclusive record fields use a linear assignment solver.

Source: Deberta.swift, BoundaryHead.swift, RecordHead.swift, Model.swift.

CLI overrides are independent: --fp16/--fp32, --tf32/--no-tf32, --cache-mb auto|N and --clear-cache/--retain-cache. A cache value of zero disables unused-buffer retention. These limits concern reusable buffers, not the total weights or total process memory.

Configuration lifetime

  • Precision changes reload the model and convert encoder weights once.
  • Cache limit and clearing policy can change between requests without reloading weights.
  • MLX runtime settings are process-wide. Model calls should be serialized, including calls across models with different cache policies.
  • Request-scoped autorelease pools release Foundation temporaries before optional MLX cache clearing.

TF32 constraints

  • MLX 0.33 caches its TF32 choice at the first relevant computation.
  • Set MLX_ENABLE_TF32 through the runtime API before any MLX workload in a host app.
  • The SDK rejects a late change after its model has started computation; the demo requires a process restart.
  • M3 has no applicable MLX NAX/TF32 path. No TF32 speedup was measured on this Mac.

F16 is approximate. In an exploratory 21-case comparison using a confidence tolerance of 0.02, small matched 20/21 cases and multi 18/21. That tolerance is looser than the F32 acceptance criterion. Deviations include a relation boundary, confidence differences exceeding 0.02 and different selected candidates. F32 with TF32 disabled is the reference-parity configuration.

Source: Runtime.swift. The demo labels are Italian: “Precisione”, “Velocità” and “Memoria ridotta”.

F32 outputs were bit-identical across the three cache configurations. Automatic cache had the lowest F32 median on these workloads. F16/automatic cache reduced median latency by approximately 9–10%, but exceeded the strict reference tolerance; it is an opt-in trade-off. These runs do not establish a peak-memory reduction for any profile.

F16 confidence differences from the same-session F32 baseline reached 0.000287235, 0.000316262 and 0.004377604 for the three texts. The longest text also reversed the order of the Torino and Bologna entities. The later paired-comparison session's F32 medians were approximately 12–14% higher than the earlier profile session. This between-session variation exceeds the observed F16 reduction; the F16 result is an observation from that session, not a statistically established general speedup.

5.4 First request and UI smoke test

In the profile session, the first recorded F32 process took 1,678.919 ms to load and 1,693.249 ms for its first request. Subsequent process loads and first-call timings benefited from system caches. These values do not support a general cold-start comparison with Rust.

A separate Release macOS demo smoke test used the short “Michele vive a Milano e lavora per Acme.” input, three labels and multi/F32/automatic cache. First call including loading: 1,251.326 ms. Four subsequent calls: 57.608, 47.763, 54.531 and 41.933 ms; JSON formatting: 0.046–0.057 ms. This is a manual UI sample, not a paired benchmark or a p95 estimate. Its timer covers the model worker and excludes rendering/actor queue delay.

Ordering exception

In the long-input case (zero-based case 7), two “Berlin” entity spans at code-point offsets [2701,2707) and [457,463) swap order. The Rust confidence range is 1.1920928955078125e-7; the MLX scores are tied. The comparator only accepts contiguous blocks of identical entity identities whose confidence range is at most 1e-6 on both sides. It records every accepted reorder. Record, relation and classification arrays remain strictly ordered.

Integration contract

  • Load local config.json, encoder_config/config.json, tokenizer.json and model.safetensors.
  • Use one serialized worker for a model. The demo uses a Swift actor; the numerical API itself is synchronous.
  • Keep the model resident between requests. Changing only the cache policy does not require weight reload.
  • Configure TF32 before any other MLX computation in the host process. The runtime cannot detect an earlier computation performed by unrelated libraries.
  • Do not interpret the 20 MiB cache limit as a 20 MiB model-memory budget.
import Foundation
import GLiNERMLX

actor Extractor {
    private let model: GLiNERModel

    init(directory: URL) throws {
        model = try GLiNERModel(
            modelDirectory: directory,
            precision: .float32,
            runtimeConfiguration: .platformDefault)
    }

    func extract(_ text: String) throws -> JSONValue {
        try model.extract(
            text,
            schema: Schema(entities: ["person", "company", "location"]),
            options: .init(includeSpans: true, includeConfidence: true))
    }
}

Additional API: extractBatch, extractLong, classifyText, classificationProbabilities, extractRelations, extractJSON, prepare, encode and updateRuntimeConfiguration.
